# エージェント支援開発ループ

## 目的

MonoLog の変更を、単発の指示ではなく再現可能な
「意図 → 実装 → 観測 → 修正 → 証跡 → 判断」のループで進めます。
ハーネスは、このループを安全かつ機械的に実行できるリポジトリ内の作業環境です。

```text
タスク契約 → 影響範囲の調査 → 最小変更とテスト → npm run check
     ↑                                                   ↓
     └──── 失敗の原因を記録して修正 ← 観測結果 ────────┘

git diff --check + npm run verify → 検証証跡 → レビュー / 人の判断
```

## タスクの入口

中規模以上の変更では、[`tasks/TEMPLATE.md`](tasks/TEMPLATE.md) を
`docs/tasks/active/<短い名前>.md` に複製してから始めます。タスク契約には、
少なくとも目的、非目標、変更可能な範囲、受け入れ条件、検証、影響範囲を記します。

小さな変更でも、開始時に次を明確にします。

- 何が利用者にとって変わるか
- 何を変えないか
- どのコマンドまたは手動操作が成功の証拠になるか

## 実行レベル

| レベル | 例 | 必要な確認 |
| --- | --- | --- |
| 低 | 文書、単体テスト、孤立したUIの小修正 | 実装者による `check` と `verify` |
| 中 | API、検索・登録フロー、複数ファイルの変更 | 受け入れ条件に対する独立レビューまたは手動確認 |
| 高 | migration、RLS、Storage、認証、削除、外部サービス | 実行前の人の判断と、所有者分離を含む追加の検証 |

高リスク領域では、現時点で再現可能なローカル検証がなければ「自動化できない」
ことを証跡に残し、推測で安全性を主張しません。

## 機械的なゲート

- `npm run check` — 短い反復用。型検査、lint、単体テスト。
- `npm run verify` — 提出前・CI用。`check` に加え本番ビルド。
- `git diff --check` — 空白エラーを検出する最終確認。

GitHub Actions では `npm ci` 後に `npm run verify` を実行します。ローカルとCIで
同じ入口を使うことで、エージェントの自己評価を実行可能な証拠に置き換えます。

## 停止・エスカレーション

次の場合は変更を拡大せず、目的、試したこと、コマンド出力、次に必要な判断を
まとめて人に渡します。

- 同じ失敗または情報不足が2回続く
- 受け入れ条件を満たすためにタスク契約外の設計変更が必要になる
- 秘密情報、本番データ、外部送信、権限、破壊的操作が必要になる
- テスト成功と利用者価値・安全性の判断が食い違う

## 学習をハーネスへ戻す

レビューや障害で同じ指摘が繰り返されたら、次のいずれかをリポジトリに追加します。

1. 回帰テストまたは統合テスト
2. lint・型・構造上の制約
3. この文書、`AGENTS.md`、または関連するタスクテンプレートの短いルール

新しいルールは、問題・適用範囲・実行できる検証を結び付けます。単に注意書きを
増やすことはしません。
